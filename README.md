# 광역의회 정책 이슈 확산 분석 시스템 (Council Issue Diffusion Analyzer)

17개 광역의회의 2024~2025년 회의록에서 정책 이슈의 최초 관측 시점, 다른 의회의 후속 논의, 향후 확산 가능성을 근거 원문과 함께 제시하는 시스템이다. 현재 개발 중이며, 핵심 이슈 40개의 이슈 카드가 자동으로 나온다. 사람 정답셋으로 정확도를 재는 일은 아직 남아 있다.

- 프로젝트 사이트: https://sijoon-sung.github.io/AI-DATA-/
- 저장소: https://github.com/sijoon-sung/AI-DATA-

## 개요

이 저장소는 KISTI가 주관하는 「2026 DATA·AI 분석 경진대회」 문제해결 부문에서 국회도서관이 출제한 문제 「광역 지방의회 회의록 기반 지방정책 이슈 트랜드 분석 및 흐름 예측」에 개인으로 참가한 프로젝트의 코드와 문서를 담고 있다. 이 프로젝트는 17개 광역의회의 2024~2025년 회의록을 분석해, 지방정책 이슈마다 주요 키워드, 데이터 범위 안에서 처음 관측된 시점, 다른 의회에서의 후속 논의 흐름, 향후 확산 가능성을 제시하는 것을 목표로 한다. 결과마다 판단 근거가 된 회의록명, 회의일자, 원문 구간을 붙인다. 또 의회 사이의 연결에는 원문에 명시적인 참조가 있는지, 아니면 시간의 선후만 있는지를 구분해 표시하며, 의회 사이의 인과관계는 단정하지 않는다.

## 현재 상태 (2026-10-11 저녁)

핵심 이슈 40개의 이슈 카드와 대회 결과표가 자동으로 나온다(`scripts/08_issue_cards.py`, GPU에서 약 20분). LLM은 쓰지 않는다. 인코더 모델(bge-m3, bge-reranker-v2-m3, KLUE-NLI로 미세조정한 KoELECTRA)과 규칙, 통계 모형, 템플릿 문장으로 만든다. 아직 사람 정답셋으로 정확도를 재지 않았다. 결과 제출 마감은 2026-11-06이다.

10/8~10/10에 키워드 입력형 다중 모델 파이프라인을 시도했지만 폐기했다. 결과표에 예시 데이터가 섞였고, 측정하지 않은 값을 확률과 요인 기여도로 표시했기 때문이다. 경위와 이후의 판단은 `docs/작업기록.md`에 있다.

## 저장소 구조

대회 제출 규정의 폴더 구성을 따른다. 아직 내용이 없는 폴더는 해당 단계에서 채우며, 최종 제출 때까지 쓰지 않은 폴더는 이 절에서 그 사실을 밝힌다.

```
(저장소 루트)
├─ README.md
├─ environment.yml         실행 환경 정의 (conda)
├─ src/                    처리 모듈
│   ├─ load.py             제공 zip 파일 읽기, zip 안 파일명 인코딩 복원
│   ├─ parse.py            회의록 HTML을 평문으로 변환
│   ├─ segment.py          본문 범위, 머리말 정보, 안건, 발언 분리
│   ├─ passages.py         발언을 문단으로 분할
│   ├─ weak_labels.py      약지도 라벨 규칙
│   ├─ issues.py           이슈 목록: 안건 제목 정규화·묶기(bge-m3), 발언 전용 정책 고유명사, 핵심 이슈 점수
│   ├─ events.py           사건표: 별칭으로 근거 문단 수집, 관련 판정(bge-reranker)
│   ├─ nli.py              한국어 NLI(KLUE-NLI로 학습한 KoELECTRA): 참조 판정, 뒷받침 검사
│   ├─ forecast.py         확산 예측: 이산시간 로지스틱, 백테스트, 보정, 등급
│   ├─ cards.py            이슈 카드 계산: 현황(가결 포함), 트렌드, 흐름과 근거 등급, 쟁점 군집, 도입 이유
│   ├─ render_card.py      이슈 카드·목차 HTML, 대회 결과표 행
│   └─ labeler/            정답셋 검수 도구 (로컬 웹 화면)
├─ scripts/                단계별 실행 스크립트 (01~08)
├─ docs/                   규정, 데이터 요약, 계획, 조사, 아키텍처, 작업기록
├─ notebooks/              심사용 실행 노트북 (01_파이프라인_실행.ipynb: 전처리 → 학습 → 추론 → 결과 확인)
├─ model/                  학습된 모델 (koelectra-klue-nli: 가중치는 저장소에 포함하지 않음)
├─ results/                이슈 카드, 대회 결과표, 예측 백테스트 (회의록 인용이 있어 저장소에 포함하지 않음)
├─ demo/                   데모 화면과 데모영상 (계획)
├─ figures/                설명용 그림 (계획)
├─ site/                   프로젝트 소개 페이지 (GitHub Pages)
├─ .github/workflows/pages.yml   소개 페이지 배포 설정
└─ data/                   제공 데이터와 가공 데이터 (저장소에 포함하지 않음)
    ├─ raw/                제공 zip 파일을 두는 곳
    ├─ processed/          스크립트가 만드는 가공 데이터
    └─ labels/             검수 표본(pool_*.jsonl, 저장소에 포함하지 않음)과 검수 결과(gold_*.jsonl)
```

`data/raw/`, `data/processed/`, 회의록 원문이 들어 있는 검수 표본(`data/labels/pool_*.jsonl`), 회의록 원문 인용이 들어갈 결과 폴더(`results/`), 참가신청서 파일(`*.hwp`), 대용량 모델 가중치 파일(`model/*.bin`, `*.safetensors`, `*.gguf`)은 `.gitignore`로 저장소에서 제외한다. 결과 폴더는 대회 제출 파일에는 넣는다.

## 실행 방법

1. conda(Miniconda 등)를 설치한다.
2. 저장소 루트에서 다음 명령으로 실행 환경을 만들고 켠다.

   ```
   conda env create -f environment.yml
   conda activate council-diffusion
   ```

3. 아래 "데이터 안내" 절에 따라 제공 zip 파일 두 개를 `data/raw/`에 둔다.
4. 저장소 루트에서 스크립트를 번호 순서대로 실행한다.

   ```
   python scripts/01_inventory.py
   python scripts/02_preprocess.py
   python scripts/02b_dedupe.py
   python scripts/03_data_summary.py
   python scripts/04_passages.py
   python scripts/05_weak_labels.py
   python scripts/06_label_pool.py
   python scripts/02c_check_segmentation.py
   ```

5. 모델을 쓰는 단계를 실행한다. NVIDIA GPU가 있으면 GPU를, 없으면 CPU를 쓴다(CPU는 훨씬 느리다). 모델은 Hugging Face에서 처음 한 번 내려받는다(bge-m3, bge-reranker-v2-m3, koelectra-base-v3-discriminator, KLUE-NLI).

   ```
   python scripts/07_train_nli.py
   python scripts/08_issue_cards.py
   ```

   카드 규칙만 바꿔 다시 만들 때는 `--reuse-events`를 붙이면 저장된 사건표와 관련 점수를 다시 쓴다. `results/issue_cards/index.html`을 브라우저로 열면 핵심 이슈 목차와 이슈 카드를 볼 수 있다. 대회 요구 항목은 `results/issue_table.csv`에 있다.

6. 검수 표본을 사람이 판정할 때는 검수 도구를 실행하고 브라우저에서 `http://127.0.0.1:8765`를 연다. 이 도구는 자기 컴퓨터(127.0.0.1)에서만 열린다.

   ```
   python src/labeler/server.py
   ```

각 스크립트의 입력과 출력은 다음과 같다. 출력 파일은 따로 적지 않으면 `data/processed/`에 저장된다.

| 스크립트 | 하는 일 | 입력 | 출력 |
|---|---|---|---|
| `01_inventory.py` | 의회·연도별 회의록 건수, 기간, 회의 종류, HTML 크기, 중복 여부를 집계하고, 의회별 HTML 구조를 조사한다 | `data/raw/`의 zip 두 개 | `inventory.csv`, `inventory_mtgnm.csv`, `inventory_html_struct.json` |
| `02_preprocess.py` | HTML을 평문으로 바꾸고 회의록, 발언, 안건 표를 만든다. HTML이 완전히 같은 중복을 표시한다 | `data/raw/`의 zip 두 개 | `docs.parquet`, `utterances.parquet`, `agenda.parquet` |
| `02b_dedupe.py` | 본문이 사실상 같은 사본을 찾아 표시하고, 분석 대상 여부(`keep`)를 정한다 | `docs.parquet` | `docs.parquet` (갱신) |
| `03_data_summary.py` | 전처리 결과의 품질을 점검하고 의회별 요약표와 의회별 고유 안건 목록을 만든다 | `docs.parquet`, `utterances.parquet`, `agenda.parquet` | `summary_by_council.csv`, `agenda_unique.parquet` |
| `04_passages.py` | 분석 대상 회의록의 발언을 400자 안팎의 문단으로 나눈다 | `docs.parquet`, `utterances.parquet` | `passages.parquet` |
| `05_weak_labels.py` | 문단마다 약지도 라벨을 만들고 그 통계를 출력한다 | `passages.parquet`, `docs.parquet` | `passages_weak.parquet` |
| `06_label_pool.py` | 과제(`ref`: 다른 지역 언급의 성격, `proc`: 의사진행 여부, `topdown`: 하향 요인)마다 약지도 라벨별로 층을 나눠, 의회가 고르게 섞이도록 검수 표본을 뽑는다. 문단마다 같은 회의록의 앞뒤 발언을 맥락으로 붙인다 | `passages_weak.parquet`, `passages.parquet`, `docs.parquet` | `data/labels/pool_{task}.jsonl` |
| `02c_check_segmentation.py` | 의회별 회귀 검사: 의원 측 발언 비율, 교육청 발언 비율, 안건 표가 빈 회의록 비율, 표본에서 놓친 발언자 줄 비율 | `docs.parquet`, `utterances.parquet` | `segmentation_check.csv` |
| `07_train_nli.py` | KoELECTRA를 KLUE-NLI로 미세조정한다(약 5분, RTX 4060) | KLUE-NLI | `model/koelectra-klue-nli/` |
| `08_issue_cards.py` | 핵심 이슈를 고르고, 사건표·관련 판정·예측을 거쳐 이슈 카드와 대회 결과표를 만든다 | `docs`, `agenda`, `passages` | `issues.parquet`, `events.parquet`, `results/` |
| `src/labeler/server.py` | 검수 표본을 한 건씩 보여 주고, 사람이 정한 라벨을 기록한다. 판단이 규칙 라벨 쪽으로 끌리지 않도록 규칙 라벨은 검수자에게 보여 주지 않는다 | `data/labels/pool_{task}.jsonl` | `data/labels/gold_{task}.jsonl` |

`02_preprocess.py`, `02b_dedupe.py`, `04_passages.py`는 의회 하나씩 처리해 파일에 이어 쓰므로, 메모리가 넉넉하지 않은 PC(16GB)에서도 돈다. 문단 ID(`pid`)는 `{doc_id}_{원문 위치}`이므로 발언 분리 규칙이 바뀌어도 같은 원문 구간은 같은 ID를 가진다.

`01_inventory.py`는 원자료를 조사하는 스크립트여서 이후 단계의 입력을 만들지 않는다. 그래서 결과를 재현할 때는 생략할 수 있다. `02b_dedupe.py`는 `02_preprocess.py`의 출력을 고쳐 쓰므로, `02_preprocess.py`를 다시 실행했다면 `02b_dedupe.py`도 다시 실행해야 한다. 이후 단계는 모두 `keep == True`인 회의록만 분석 대상으로 삼는다.

모델 학습, 추론, 평가는 다음과 같다. 자세한 설계는 `docs/04_아키텍처.md`에 있다.

- **학습**: 학습하는 모델은 한국어 NLI 판정기 하나다. KoELECTRA(base)를 KLUE-NLI 학습셋 24,998쌍으로 3에폭 미세조정하고, KLUE-NLI 검증셋 3,000쌍으로 평가한다. 지표와 설정은 `model/koelectra-klue-nli/metrics.json`에 저장된다.
- **추론**: `08_issue_cards.py`가 ① 안건 제목을 정규화해 bge-m3로 묶어 정책 수단을 만들고 핵심 이슈를 고른다. ② 이슈 별칭(띄어쓰기 무시 정규식)으로 문단 368만 개에서 후보를 모으고, 후보 전부를 bge-reranker-v2-m3로 "이 문단이 이 이슈를 말하는가" 점수를 매긴다. ③ 별칭마다 관련 비율(점수 0.5 이상 비율)을 재서, 대표 별칭보다 비율이 크게 낮은 넓은 별칭으로만 걸린 문단은 점수 0.5 이상일 때만 쓴다(이름만 같은 다른 이야기를 거른다). 점수 0.5 이상인 가장 이른 문단을 "확인된 최초 관측"으로 쓴다. ④ 다른 의회의 정책을 언급한 문장은 규칙으로 찾은 뒤 NLI 판정기로 거른다. ⑤ 이슈 카드의 문장은 템플릿으로 채우고, 인용은 원문 문단과 글자 일치를 검사한다. LLM은 쓰지 않는다.
- **평가**: 확산 예측은 결과 창이 겹치지 않는 두 기준점(2025-01-01, 2025-07-01)에서 백테스트한다(AUC, Brier 기술 점수, 등급별 실측 빈도와 95% 신뢰구간, 같은 이슈 안 AUC). 결과는 `results/forecast_backtest.json`에 저장된다. 관련 판정과 참조 판정의 정확도는 사람 정답셋(검수 도구로 작성 중)으로 잴 계획이며, 아직 재지 않았다.


## 데이터 안내

이 저장소에는 대회 제공 데이터와 그로부터 만든 가공 데이터가 들어 있지 않다. 제공 데이터의 출처는 각 광역 지방의회이며, 대회 규정상 경진대회 외의 목적으로 쓸 수 없다. 또 참가신청서의 서약에 따라 승인받지 않은 제3자에게 열람하게 하거나 제공할 수 없고, 대회가 끝나면 폐기해야 한다.

코드를 실행하려면 대회에서 받은 zip 파일 두 개를 다음 이름 그대로 `data/raw/`에 둔다. 압축은 풀지 않는다. 스크립트가 zip 파일을 직접 읽는다.

```
data/raw/2024_광역 회의록.zip
data/raw/2025_광역 회의록.zip
```

참고로 zip 안의 의회별 JSON 파일 이름은 CP949로 저장되어 있지만 UTF-8 표시가 없어서, 그대로 읽으면 이름이 깨진다. `src/load.py`가 이 이름을 자동으로 복원하므로 따로 처리할 필요는 없다. 전남광주통합특별시의회 파일은 두 해 모두 비어 있으므로, 분석 대상은 17개 의회다.

## 대회 규정 준수 요약

- **상용 API를 쓰지 않는다.** 제공 데이터를 처리하는 모든 모델은 오픈 모델이며 로컬에서 실행한다. 현재 계획에서는 실행에 외부 AI 서비스나 API가 필요하지 않으므로, 심사용 인증정보도 따로 제공할 것이 없다.
- **분석 기간 밖의 정보를 쓰지 않는다.** 분석과 예측은 2024-01-01부터 2025-12-31까지의 회의록만으로 한다. 2026년의 사건(전남광주 통합 등)은 쓰지 않는다.
- **인과를 단정하지 않는다.** 의회 사이의 연결마다 근거 수준을 붙인다. 원문에 명시적 참조가 있으면 "명시적 참조"로, 시간 선후만 있으면 "선행 관측", "후행 관측"으로만 쓴다.
- **근거를 붙인다.** 모든 판정 결과는 회의록 식별자와 원문 문자 위치(시작, 끝)를 가지므로, 회의록명, 회의일자, 원문 구간을 함께 낼 수 있다.
- **제공 데이터를 공개하지 않는다.** 원자료와 가공 데이터는 저장소에 올리지 않고, 대회가 끝나면 폐기한다. 결과표를 만들 때는 민원인 등 일반인의 정보가 인용 구간에 들어가지 않는지 점검한다.
- **개인정보와 인증정보를 넣지 않는다.** 연락처가 들어 있는 참가신청서 파일은 `.gitignore`로 제외했다.
- **라이선스가 명시된 모델만 쓴다.** 위 "사용 모델과 라이선스" 절을 참조한다.
- **AI 활용 기록을 남긴다.** 개발 과정에서 Claude Code(Anthropic)를 문제 분석, 선행연구와 사례 조사, 코드 작성, 문서 작성의 보조 도구로 썼다. 주요 판단, 버린 대안, 실패 사례는 `docs/작업기록.md`에 날짜별로 쌓고 있으며, 제출 때 규정의 "AI 활용범위와 주요 검토 과정" 여섯 항목으로 정리한다. 제공 데이터를 분석하는 제출 시스템에는 상용 API를 쓰지 않는다.
