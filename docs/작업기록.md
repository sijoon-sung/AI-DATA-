# 작업 기록

제출 규정의 "AI 활용범위 및 주요 검토 과정" 여섯 항목(활용 도구, 활용 단계, 주요 활용 내용, 참가자의 기여와 검증, 검토한 대안과 실패 사례, 최종 선택 이유)을 쓰기 위한 기록이다. 주요 판단과 버린 대안을 날짜순으로 쌓는다.

## 2026-10-05

- 문제 정의: 처음에는 "지방에서 국회로" 올라가는 수직 흐름을 중심축으로 삼았다. 그러나 문제 원문을 다시 대조해 보니 중심은 의회 간 수평 흐름과 확산 예측이었다. 그래서 원문의 네 항목(이슈 키워드, 최초 관측, 후속 흐름, 확산 가능성)을 필수 코어로 되돌렸다. 수직 흐름은 건의안·결의안 신호라는 보조 지표로 낮췄다.
- 예측 대상: "다음에 어느 의회 하나로 가는가"는 쓸모가 약하다고 판단했다. 그래서 "몇 개 의회까지, 얼마나 빨리 퍼지는가"를 주 대상으로 하고, 의회별 확률은 세부 결과로 두었다.
- 규정 반영: 상용 LLM API 금지와 기간 외 정보 금지 규정을 확인했다. 그래서 모든 모델을 로컬 오픈 모델로 정하고, 2026년 정보(전남광주 통합 등)를 예측에서 제외했다.

## 2026-10-06

- 전처리: 의회마다 회의록 웹 시스템이 달라 발언자 표기가 두 형식(A형, B형)으로 나뉘는 것을 확인했다. 문서마다 두 형식의 매칭 수를 비교해 많은 쪽을 쓰도록 했다.
- 중복 발견: HTML 완전 중복 378건에 더해, HTML은 조금 다르지만 본문이 같은 사본 2,117건을 찾았다. 특히 2025년 파일 다수에 회의록이 두 벌씩 들어 있었다. 이를 처리하지 않으면 2025년 논의량이 두 배로 보인다. 같은 의회, 같은 날짜 안에서 길이 비율과 앞뒤 구간 유사도로 판정해 긴 쪽만 남겼다.
- 검토 후 버린 방법: 회의록명(`MINTS_NM`)과 날짜로 중복을 찾는 방법을 검토했다. 그러나 강원처럼 회의명이 모두 "기타"인 의회에서는 서로 다른 위원회가 같은 이름을 가져서 쓸 수 없었다. 그래서 본문 비교 방식을 택했다.
- 모델 선택: 분류기 기본 모델로 `klue/roberta-base`를 검토했으나, 모델 카드에 라이선스가 명시되어 있지 않았다. "저작권 문제가 해결된 도구만 사용" 규정에 맞추기 위해 Apache-2.0이 명시된 KoELECTRA로 바꾸었다. EXAONE 3.5와 Qwen2.5-3B는 라이선스가 비상업 또는 연구 조건이어서 제외했다.
- 아키텍처: 의미 판단 다섯 지점을 딥러닝 모델이 맡고, 결정적인 처리는 규칙으로 두는 구조로 정했다.
- 문단 분할(L1): 발언 3,229,774개를 400자 안팎의 문단 3,563,803개로 나눴다. 36.4%는 30자 미만("예." 등)이어서 판정 대상에서 뺀다.
- 약지도 라벨(L2): 30자 이상 문단 2,266,277개 중 다른 시도를 언급한 문단은 37,169개(1.6%)였고, 그중 의원 측 발언은 23,709개였다. 규칙상 '정책 참조' 후보인 의원 발언은 4,456개(의회별 118~568개)였다. 그래서 "명시적 참조가 충분히 있는가"라는 가정은 학습과 검수에 필요한 양으로는 확인되었다고 판단한다. 다만 이슈 하나당으로 나누면 적을 것으로 본다.
- 발견한 오류 가능성: '광주'는 경기도 광주시와 구분되지 않아 광주광역시 참조 수(410)가 과대 집계되었을 수 있다. '대전환', '대전제', '부산물'처럼 지역명이 아닌 단어는 사전에서 제외했다.

## 2026-10-08 ~ 10-10 (폐기한 시도)

- 시도: 사용자가 키워드("트램, 지하철, 교통수단" 등)를 넣으면 규칙과 임베딩으로 관련 문단을 모으고, 다섯 개의 "모델"(의제 인출, 맥락 분류, 엣지 추론, 확산 예측, 보고서 합성)을 거쳐 대회 예시 형식의 결과표를 만드는 파이프라인을 만들었다. 파일은 `_archive/2026-10-10_다중모델_시도/`에 로컬로만 보관한다.
- 10/11 점검에서 발견한 문제:
  - 결과표 9행 중 7행이 코드에 직접 적어 넣은 예시 데이터였다(가짜 회의록 ID `DOC-JB-20240214` 등). "청년 · 정책", "AI · 정책" 행은 근거가 대전 트램 발언이었다.
  - "SHAP 요인 분해"와 "확률"이라고 표시한 값이 실제로는 고정 가중치(0.40/0.25/0.20/0.15) 합을 비율로 나눈 것이었다. 엣지 신뢰도(0.95, 0.88, 0.70)도 측정값이 아닌 상수였다.
  - 의회별 통계 수치(재정자립도 등)에 출처가 없었다. 기간 안 외부자료를 써도 되는지도 확인되지 않은 상태였다.
  - 심사용 노트북이 존재하지 않는 클래스를 불러 첫 셀에서 멈췄다. 임베딩 모델 `jhgan/ko-sroberta-multitask`는 라이선스 확인 표에 없었다. torch 등이 환경 파일에 없어서 재현되지 않았다.
  - 이 작업은 GitHub에 올라가지 않았다.
- 판단: 고치기보다 버리기로 했다. 키워드를 사람이 넣는 방식은 이슈를 "도출"하라는 문제 요구에 맞지 않고, 측정하지 않은 수치를 결과에 쓴 것은 근거 제시 원칙에 어긋난다.
- 살린 아이디어: 정책 앵커 정규식(조례·기금·제도명 추출)은 이슈 연결의 규칙 기준선으로, 3단계 근거 수준(명시적 참조 / 상위법 공통대응 / 시간 선후)은 L4 엣지 체계로 다시 쓴다. 고정 신뢰도 상수는 버린다.
- 교훈(재정비 원칙으로 반영): 결과에 나오는 수치는 모두 실데이터로 잰 값이어야 한다. 기법 이름은 실제로 그 기법을 썼을 때만 붙인다. 결과표는 스크립트가 처음부터 다시 만들어야 한다.

## 2026-10-11

- 재정비 계획(`05_재정비_계획.md`): 심사 기준(창의성 20, 우수성 50, 효과성 30과 문제별 기준 두 가지)에 맞춰 단계와 일정을 다시 짰다. 혼자 26일 안에 끝내야 해서 범위를 줄였다. 확산 예측은 GRU+GAT 대신 로지스틱 기준선과 LightGBM+TreeSHAP을, 서술은 LLM 대신 템플릿을 기본으로 한다.
- 아이디어 검토(`06_아이디어_검토.md`): 단순한 시스템이 틀리는 다섯 지점(시간 선후를 확산으로 착각, 데이터 시작점, 회의 일정, 키워드 오탐, 이슈 정의)을 정리하고, 이를 막는 아이디어 22개의 우선순위를 정했다.
- 데이터로 가정을 확인했다(06 문서 9절).
  - 조례안 제목을 정규화하면 3곳 이상 의회에서 제정된 조례가 240개다. 예측 모형을 학습할 수 있는 규모다.
  - 가장 넓게 퍼진 조례(도심복합개발 지원, 14곳이 6개월 안에 제정)는 법 시행에 따른 동시 대응으로 보인다. 그래서 공통 외부요인 탐지를 가장 먼저 하기로 했다.
  - 회의는 회기가 있는 달에만 열린다(경기 24개월 중 9개월이 0건). 월 단위로 선후를 말하면 회기 일정을 재게 된다.
  - 서울 외 의회의 '서울' 언급은 대부분 지리나 수도권 비교였다. 규칙 라벨의 "서울 1,397회 참조"를 선도 의회의 증거로 읽지 않기로 했다.
- 실행 환경: README와 환경 파일은 uv 기준이었지만 실제로는 conda로 작업했다. 제출 환경과 실제로 돌린 환경을 같게 하려고 conda로 통일했다. 개발 환경의 버전을 그대로 고정한 `environment.yml`을 만들고 uv 파일은 지웠다.
- 저장소: 로컬 폴더를 GitHub 저장소에 다시 연결했다. 로컬에서 빠져 있던 소개 페이지 이미지 3개를 GitHub에서 되살렸다. 결과 폴더(`results/`)는 회의록 원문 인용이 들어가므로 공개 저장소에서 제외하고 제출 파일에만 넣기로 했다.
